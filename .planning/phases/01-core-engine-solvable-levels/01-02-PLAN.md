Author the 20 Phase 1 level layouts and implement a build-time solvable level generator. Every level must be guaranteed solvable, use only even-count faces, and stay within the PRD tile/layer budget.

Purpose: Levels are data, not runtime guesswork. Generating them at build time guarantees the solvability contract while keeping the game startup fast.
Output: `public/levels/1.json` through `public/levels/20.json`, plus a `npm run generate-levels` command that reproduces them deterministically.
</objective>

  <behavior>
    - SolvableDealer.deal(layout, faces, rng) returns a Level with all positions assigned faces in pairs.
    - Every assigned face appears an even number of times.
    - Solver.isSolvable returns true for the generated Level.
    - Using the same seed produces identical face assignments.
  </behavior>
  <action>
    Create `src/generator/SolvableDealer.ts` exporting a `SolvableDealer` class with a static `deal(layout: LevelLayout, faces: number[], rng: () => number): Level` method. The method: creates `Stone` objects from positions with `face: -1` and `picked: false`; duplicates each face id into pairs and shuffles the pair list using the supplied RNG; iterates the shuffled faces, and for each face finds all stones that are currently not picked and not blocked (using the same `isBlocked` logic as BoardModel), picks two of them at random using the RNG, assigns the face to both, and marks both as `picked = true` to expose deeper tiles; after all faces are assigned, resets every stone's `picked` to false and returns a `Level` object with id, name, stones, theme, and maxLayer. If at any step fewer than two free stones are available, throw a clear error naming the level so the build fails. Implement a deterministic seeded RNG `createSeededRng(seed: string)` in the same file using a simple mulberry32 or splitmix32 algorithm (no external dependency). Export a constant `DEFAULT_SEED = 'vita-mahjong-v1'` matching D-08. Create `src/__tests__/generator.test.ts` with tests that: verify all faces appear an even number of times; verify the dealer succeeds for level 1; verify deterministic output for the same seed; and verify a tiny dead-end layout throws.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Build script → level JSON | Generated data crosses from build-time Node context to runtime load context. |
| Layout definitions → generator | Fixed layout arrays must not be executed or eval'd. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | npm/pip package installs | high | mitigate | No new packages are added in this plan; reuse the packages installed in Plan 01-01 and verified in 01-RESEARCH.md §Package Legitimacy Audit. |
| T-01-SC | Tampering | npm/pip package legitimacy checkpoint | high | mitigate | If `tsx` or any generator dependency is not already covered by the 01-RESEARCH.md audit, cross-check it on npmjs.com before install. Current audit covers TypeScript and Node tooling as OK/Approved. |
| T-01-02 | Tampering | Generated level JSON | medium | mitigate | Runtime loader validates the JSON schema (id, name, theme, stones array with even face counts, maxLayer ≤7, stone count ≤128) and rejects malformed files. The generator never uses `eval` or dynamic code on layout data. |
| T-01-03 | Denial of Service | Solver during generation | medium | mitigate | Generator caps solver verification time; build fails fast on an unsolvable level rather than hanging. Layout budgets are capped at 128 tiles / 7 layers per LVLS-02. |
| T-01-04 | Information Disclosure | Build logs | low | accept | Level seeds are public (D-08); no secrets are logged. Accept minimal disclosure of deterministic level data in build output. |
</threat_model>
